# Mekane Selam Senbet School - Feature & Data Flow Test Matrix

A companion to `DEVELOPER_HANDOVER.md`. That document explains how the system is built. This one lists **every feature you can click**, and for each one traces **where its data comes from and where it goes**, so you can walk the whole system and check that a value stays the same value from the moment someone types it to the moment someone else reads it.

Generated from the code on 2026-08-02, against `main` @ `d1336bb`.

## How to read this document

Every row has four columns.

| Column | What it tells you |
|---|---|
| **Feature** | What the thing is, and where to click it. `page` = the screen, `API` = the endpoint behind it. |
| **Data in** | Every value the step consumes, tagged with where that value originated. |
| **Data out** | Which tables and side effects the step writes, and which values the server derives rather than accepts. |
| **Test it / edge cases** | The specific things to try, including the ones that are known to behave oddly. |

### Origin tags

The point of this document is the tags. When you test a chain, follow the `[P]` values - those are the ones that can silently drift.

| Tag | Meaning | Why it matters when testing |
|---|---|---|
| **[U]** | **User input.** A human typed or picked it in this step. | Test validation, empty, too long, wrong type, duplicates, and non-Latin (Amharic) text. |
| **[P]** | **From a previous process.** It arrived from an earlier feature's output. | This is where consistency breaks. Check the value still matches its source after the earlier step is edited, archived, or reversed. |
| **[A]** | **Auto-generated.** The server or database produced it - ids, timestamps, derived status, computed rates. | You cannot type these. Check they are correct, and check they update when their inputs change. |
| **[S]** | **From settings or seed data.** `app_settings`, a migration seed, or a hardcoded constant. | Change the setting, then confirm every consumer picks up the new value. |

### The golden rule for consistency testing

For any value tagged `[P]`, ask three questions:

1. **Does it still match its source right now?** (Enter it, then read it in the downstream screen.)
2. **What happens if the source is edited afterwards?** (Does the downstream copy follow, or is it a frozen snapshot? Both are valid designs - you need to know which.)
3. **What happens if the source is archived or deleted?** (Does the downstream row disappear, keep a stale label, or break the page?)

Section 15 lists the chains that are already known to break one of these. Read it before you file a bug, so you do not re-report a known dead-end.

## 13. Notifications - the cross-cutting chain

Every producer writes through one function (`notify()`); every inbox reads through one query builder. Test the chain end to end for each producer.

| Producer (what triggers it) | Target | Who should receive it | Who must **not** |
|---|---|---|---|
| Admin composes an announcement | role / department / class / person **[U]** | Exactly the chosen audience | Everyone else. Check at least one other role each time. |
| Teacher posts an announcement | Their department, or one class | Department members, or the class's students + parents + teachers | Other departments |
| Teacher proposes an event | Heads of that department | Those heads | The proposer themselves, if they are also a head |
| Head approves / rejects an event | The proposer | The proposer | Nobody else |
| Public registration submitted | All admins + heads of the form's department | Both | Heads of other departments |
| Admin generates payments | Each charged student | Only students who got a **new** row | Students who were skipped, and everyone when the amount is 0 |
| Admin closes or reopens a term | All teachers | Every teacher | Students and parents |
| Person assigned to a department | That person | Teachers only | Students (deliberately not notified) |

**Read state:** marking a notification read writes to `notification_reads`. Mark the same one read twice - it must not error or double up. Open the same account in two browsers, mark read in one, reload the other.

## 14. Cross-module chains worth walking end to end

These are the scenarios where a `[P]` value passes through three or more features. Walk each one in a single sitting.

| # | Chain | What to verify at each hop |
|---|---|---|
| 1 | **New member → graded → reported** | Admin creates a student with a login → enrols them in a class → assigns a teacher to that class+subject → teacher enters a grade → the score is identical in the student portal, the parent portal and the admin grades screen → teacher finalizes → teacher blocked (423), admin still allowed → admin closes the term → **both** blocked. |
| 2 | **Attendance → percentage → eligibility** | Teacher takes roll-call on a date inside the current term → the session gets the right `term_id` → the teacher's "this term" column matches a hand calculation → the same person's rate appears in the staff eligibility table → lower the threshold in Settings → the eligible flag flips. |
| 3 | **Charge → notification → balance** | Admin sets a term's `default_tuition` → bulk-generates for one class → each student gets exactly one row → each gets a bell notification → the student's outstanding balance matches → admin records a part-payment → status becomes partial everywhere → run generation again → 0 created. |
| 4 | **Proposal → approval → public** | Teacher proposes an event → the head is notified → not on the public site yet → head approves → the proposer is notified → it is now on the public site → admin sees the truthful status pill. |
| 5 | **Public sign-up → staff action** | Visitor submits a form → admins and the owning department's heads are notified → the submission is visible in both the admin and the (scoped) staff screen → the labels snapshot survives a later field rename → status moves new → seen → contacted. |
| 6 | **Rename → everywhere** | Rename a teacher in admin → the new name appears in the class list, the department members list (which reads `people`), the eligibility table, and as the "updated by" on grades they entered. |
| 7 | **Archive → cleanup** | Archive a student → they vanish from the teacher's roster and the parent portal → **then check whether they still appear in eligibility and still receive generated payments** (see section 15). |

## 15. Known inconsistencies and dead-ends

**Read this before filing bugs.** These are real behaviours in the current code. Some are deliberate and deferred, some are genuine defects. Confirm them rather than rediscover them.

| # | What you will see | Why | Status |
|---|---|---|---|
| 1 | **Archived students still get payment rows** from bulk generation. | Generation selects from `student_class_assignments` alone and never joins `students`, so archiving a user (which archives their profile but not their enrolment) leaves them in scope. | Defect. Worth fixing. |
| 2 | **A zero-amount charge gets a different status depending on how you create it.** Bulk generate with amount 0 → `paid`. Create manually with amount 0 and paid 0 → `unpaid`. | Two separate derivation rules: an inline ternary in `payments/generate.php`, and `derive_status()` in `payments/index.php`. | Defect. One rule should win. |
| 3 | **`status` on a payment can contradict the amounts.** | The API accepts a client-supplied status without checking it against `amount` / `paid_amount`. | Defect, low severity. |
| 4 | **Department roll-call attendance counts towards nothing.** Teachers can record it; eligibility, dashboards and summaries all read class sessions only. | Eligibility filters `context_type='class'` by design. | Known dead-end, deferred. |
| 5 | **Attendance taken on a date outside every term has no term** and so is invisible in every "this term" view, while still counting in the all-time numbers. | The term is derived from the session date; a gap between terms yields null. | Working as designed - but it means term dates must have no gaps. |
| 6 | **A session's term is fixed when the session is created.** Editing the roll-call later, or changing the term's dates afterwards, does not re-derive it. | `term_id` is stamped at insert only. | Working as designed. Re-check after any term-date edit. |
| 7 | **Tasks / homework have no reader.** Teachers create them; no student or parent screen displays them. | The consumer was never built. | Known gap - Phase 2.5 will either expose it or formally park it. |
| 8 | **Registration submissions never become people or students,** and applicants are never told the outcome. | No user link exists on a submission; `new/seen/contacted` is internal triage. | Known gap - Phase 4. |
| 9 | **A registration submission can be archived but not unarchived.** | No unarchive action exists. | Known gap - Phase 4. |
| 10 | **The applicant's name on a submission is a guess** - the first text field whose English label contains "name". | A heuristic, because forms are freely configurable. | Known limitation. |
| 11 | **The student's attendance % differs from the teacher's "this term" %.** | The student view is deliberately all-time; the teacher view is term-scoped. | Working as designed. |
| 12 | **Serving eligibility uses the all-time rate, even though a term rate is displayed next to it.** | Changing what makes someone eligible was deferred. | Working as designed - Phase 6. |
| 13 | **Eligibility counts a person's attendance from every class they have ever attended,** not only the department's own classes. | It is an academic-attendance measure, not a departmental one. | Working as designed. |
| 14 | **Archiving a user does not archive their `people` row, department memberships or class enrolments.** | Only `users` and the role profile are archived. | Root cause of #1. |
| 15 | **The teacher's roll-call defaults everyone to "present".** | The roster pre-fills `present` for unmarked students. | Working as designed, but easy to save by accident. |
| 16 | **The teacher announcement endpoint writes to `notifications` directly** instead of going through `notify()`. | It predates the choke point and happens to write a valid row shape. | Latent drift risk. The row is currently correct - verify it stays correct. |
| 17 | **`notifications.read_by` still exists** alongside the `notification_reads` table. | Kept for rollback safety in migration 022. | Deliberate. Dropped in a later phase. |
| 18 | **The migrate endpoint lives under `/api/admin/` but is not admin-guarded** - it is protected by a deploy token. | Deployment tooling, not an admin feature. | Working as designed. Confirm the token is required. |
| 19 | **Production returns a server error on the public registration API.** | Migrations 019-024 have never been applied to production. | Blocked on the next deploy + migrate. |
